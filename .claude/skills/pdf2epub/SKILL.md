# pdf2epub: working on this repository

The converter turns a PDF into a reflowable single-column EPUB 3 for reading on a phone through Kindle,
without losing fidelity: formulas, figures and tables are cropped from a high-DPI render of the page, and
everything else becomes real text. `README.md` covers the user-facing features. This skill covers how to
work here: converting, checking quality, changing code, and delivering results.

For the module map, the main heuristics and their known traps, read
[`reference/architecture.md`](reference/architecture.md) before changing converter code.

## Ground rules

1. **The corpus is the yardstick.** `demo/` holds every conversion ever delivered or used for development:
   `<name>.pdf`, the accepted `<name>.epub`, and a `<name>.quality.json` baseline, where `<name>` is
   `{title_in_snake_case}-{arxiv_id}` (e.g. `attention_is_all_you_need-1706.03762`; `pdf2epub.naming`
   builds it, and a test enforces it). **Commit converter
   code only when `python tools/corpus_gate.py` passes on every entry and improves at least one.** A fix
   that helps one paper but makes another worse is not done. Either find a version that is neutral
   elsewhere, or ask the user about the trade-off before you `--force` it.
2. **Every conversion you deliver goes into the corpus** (`--add`, below), committed next to its PDF, so
   later changes are measured against it.
3. **Code and the outputs it produces are committed together.** After a passing gate, `--update` rewrites
   the EPUBs and baselines in `demo/`. Commit those files in the same commit as the code, so the
   `*.quality.json` diff shows what improved.
4. **Metric changes are separate commits.** If you change `src/pdf2epub/quality.py` (a lint rule, a
   metric), you changed the yardstick, not the conversions. Run `python tools/corpus_gate.py --rescore`,
   which re-scores the committed EPUBs without converting anything, and commit that alone with
   `quality.py`. Only then judge converter changes against the new numbers.
5. **Never hand-edit** files in `demo/`. They are generated by `tools/corpus_gate.py`.
6. **The repository is public.** Never write the user's email address, tokens or other personal data
   into any file. Get the user's address from the session context when you need it. Before committing a
   PDF that is not openly published (anything other than arXiv-style public papers), ask the user.

## Setup

```bash
python -m venv .venv && .venv/bin/pip install -e ".[dev,qa]"   # qa = playwright, for phone previews
.venv/bin/python -m pytest -q -m "not corpus"                  # fast tests (~5 s)
```

Optional tools:

- EPUBCheck: download `epubcheck-5.1.0.zip` from <https://github.com/w3c/epubcheck/releases>, unzip it
  outside the repo, then run `java -jar epubcheck-5.1.0/epubcheck.jar book.epub`. Setting
  `EPUBCHECK_JAR=...` makes `pytest` validate output too.
- Chromium for `tools/phone_preview.py` is found automatically under `/opt/pw-browsers` (Claude Code
  cloud sessions). Elsewhere, set `PDF2EPUB_CHROMIUM` or run `playwright install chromium`.

## Workflow A: convert a paper and send it to the user's phone

1. **Get the PDF.** For arXiv, use `curl -fsSL -o /tmp/in/<id>.pdf https://arxiv.org/pdf/<id>` and put
   downloads in their own directory. For a user upload, use the uploaded path.
2. **Convert:** `.venv/bin/pdf2epub convert /tmp/in/<id>.pdf`. Because the file name contains the arXiv
   id, the EPUB is written next to it as `{title_in_snake_case}-{id}.epub`. Pass `--title`/`-a` only if
   the detected metadata is wrong; the corpus records those options (and the title names the files).
3. **Run the quality pass** (Workflow B) and fix what it finds. Converter fixes follow Workflow C.
4. **Add it to the corpus:**
   `.venv/bin/python tools/corpus_gate.py --add /tmp/in/<id>.pdf [--title "..." -a "..."]`.
   This converts it with the current code and writes `demo/<name>.pdf`, `.epub` and `.quality.json`
   with `<name>` = `{title_in_snake_case}-{id}`, plus the regenerated `demo/README.md` index. It takes
   the arXiv id from the file name; pass `--arxiv <id>` for an upload whose name lacks it. It refuses
   an arXiv id that is already in the corpus. Note the `<name>` it prints for the next steps.
5. **Commit and push** `demo/<name>.*` and `demo/README.md` to the branch the user's link should point
   to (normally `main`).
6. **Verify the download link** before sending it. Raw files are served at
   `https://github.com/mgbvox/pdf2epub/raw/<branch>/demo/<name>.epub`:
   ```bash
   curl -fsSL -o /tmp/check.epub "https://github.com/mgbvox/pdf2epub/raw/main/demo/<name>.epub" \
     && cmp /tmp/check.epub demo/<name>.epub && echo "link OK"
   ```
   A fresh push can take a few seconds to be served. Retry `curl` before concluding it failed.
7. **Email the link** with the Gmail connector (`send_message`; load it with ToolSearch if it is
   deferred). Send it to the user's own address taken from the session context. Include:
   - the direct `.../raw/main/demo/<name>.epub` link (one tap downloads it on Android; the file name
     carries the title, so it is recognisable in the Kindle library and downloads folder);
   - the paper title and what was checked (e.g. "EPUBCheck clean, 0 lint issues");
   - the Kindle steps below.

   **Why a link and not an attachment:** the connector takes attachments as base64 text inside the tool
   call, which is impractical for EPUBs of several MB. A pushed file plus a verified link is reliable and
   leaves the book in the corpus. If the repository ever becomes private, the raw link needs a GitHub
   login. In that case, ask the user how they want to receive files.

**Reading it on Kindle (put this in the email):** the Kindle app does not open an `.epub` tapped in a
file manager or browser; the phone just vibrates or nothing happens. Use **Send to Kindle**:

- Android share sheet: open the download, Share → Kindle.
- Or email the file as an attachment to the user's `@kindle.com` address (Kindle settings → "Send to
  Kindle email").
- Or upload it at <https://www.amazon.com/sendtokindle>.

### Web articles (HTML instead of PDF)

For a blog post or web paper, use `.venv/bin/pdf2epub web URL [MORE_URLS...] -o /tmp/out/<name>.epub`.
Pass the article plus pages it links as part of itself (e.g. a separate appendix page) to get one book.
Name the file `{title_in_snake_case}` (plus `-{arxiv_id}` if the work has one); without `-o` that is the
default. Quality pass: run EPUBCheck, look at phone previews (light and `--dark`), and compare the text
with the live page. `pdf2epub check` needs a PDF, so instead diff the words against the page's
`main.innerText` (as `quality.epub_words` does). `src/pdf2epub/web.py` documents the DOM rules; extend
them when a site's markup is not handled, and add a case to `tests/test_web.py`.

**Web articles are usually third-party content without an open license.** Their text, snapshots and
EPUBs must not be pushed to this public repository. Deliver the EPUB privately: send the file to the
user's app (e.g. the session's file-sending tool), not as a public link.

The web converter has its own corpus section: `python tools/corpus_gate.py --add-web URL [URL...]`. It
commits only `demo/web/<name>.quality.json` (URLs, options, quality baseline, a fingerprint of the page
text). The MHTML snapshots, reference text and accepted EPUB go in the git-ignored `.corpus/web/<name>/`.
The gate (`--web-only` / `--pdf-only` to narrow it) converts from those snapshots and re-captures them from
the live URLs when the cache is empty. If the page itself has changed, the entry reports `SOURCE CHANGED`
instead of a comparison; review the new conversion, then `--update`. Changes to `src/pdf2epub/web.py`
follow the same rule as converter changes: the gate must pass on the web entries.

## Workflow B: quality pass and refinement of one conversion

Work through these steps in order. Every EPUB block carries `data-page="N"` (1-based PDF page), so every
finding maps back to a page of the source.

1. **Automated score:** `.venv/bin/pdf2epub check paper.pdf paper.epub`. It prints the fidelity metrics,
   structure counts, and every lint issue with its PDF page. For a corpus entry,
   `python tools/corpus_gate.py <arxiv-id> --show-issues` does the same and compares with the baseline
   (entries can be selected by arXiv id or full name).
   - `word_recall` / `word_precision` (text dropped / duplicated; alt text counts),
     `bigram_*` (local word order), `order_score` (block order; 1.0 is perfect).
     Recall around 0.85–0.97 is normal: words inside figure, table and equation images count as missing.
   - Lint kinds, the usual causes, and where to look:

     | kind | usual cause | look at |
     | --- | --- | --- |
     | `split-paragraph` | paragraph broken at a line, column, float or page | `structure._continues`, `ended_short`, `_frames` |
     | `stray-fragment` | a few words alone: lost heading, caption piece, label | `_heading_like`, caption detection |
     | `hyphen-leftover` | `exam- ple` not joined | `structure` de-hyphenation, `stats.vocab` |
     | `hard-breaks` | `<br>` inside body text (grid/centred rows) | `_grid_rows`, `keep_breaks` |
     | `tall-inline-math` / `wide-inline-math` | display math treated as inline, or a stray glyph pulled into a run | `layout.detect_equations`, `extract.build_rows` |
     | `blank-image` | crop of nothing (mask or region bug) | `render.crop`, region boxes |
     | `long-word` | words glued (spacing) | `extract.needs_space` |
     | `caption-gap` | Figure/Table N never captioned: caption attached to the wrong float or lost | `layout.region_for_caption` |
     | `duplicate-paragraph`, `empty-paragraph` | text emitted twice / empty block | `structure._assemble` |
2. **EPUBCheck:** `java -jar epubcheck.jar paper.epub`. It must report 0 errors and 0 warnings.
3. **Look at the source pages:** `.venv/bin/pdf2epub inspect paper.pdf --pages 3,7 --out /tmp/insp`, then
   view `page-003.png`. It overlays the detected layout, numbered in reading order. Colours: figure blue,
   table green, text box purple, equation orange, algorithm black, caption cyan, text grey with order
   numbers, footnote brown, dropped running heads red, columns magenta. Most defects are visible here: a
   region swallowing text from the next column, a caption attached to the wrong float, an equation
   detected only in part, rows numbered in the wrong order.
4. **Look at the result as a phone shows it:**
   `.venv/bin/python tools/phone_preview.py paper.epub /tmp/prev --chapters ch003 --screens 3`, and again
   with `--dark` (Kindle dark mode: check that formula images stay legible). Chapter files are
   `OEBPS/text/chNNN.xhtml`; `unzip -l paper.epub` lists them. Check these on the screenshots: formulas
   and tables are legible at phone width, nothing is clipped, inline math sits on the baseline, and the
   text reads as one column in the right order.
5. **Compare with the PDF, block by block,** for the pages that look suspicious. Be adversarial: hunt for
   lost text, wrong order, captions on the wrong figure, garbled ligatures (`suffxi`), and split equations.
6. **Refine.** If a document-level option is enough, re-convert with it:
   - `--inline-math image` if inline formulas render badly as text;
   - `--no-split-panels` if side-by-side sub-figures are split wrongly;
   - `--rotate-wide` for very wide tables;
   - `--dpi 600` for very dense figures (the default is 400);
   - `--title` / `-a` if the metadata is wrong; `--pages 1-12` to drop appendices the user doesn't want.

   If the defect is the converter's fault, fix the code (Workflow C), not just this file. The fix must
   hold up on the whole corpus.

## Workflow C: improve the converter

1. **Reproduce on one page.** Use `pdf2epub inspect --pages N` to see the layout. To trace the
   intermediate stages in Python:
   ```python
   from pdf2epub.converter import analyze, build_document
   doc, pages, stats, layouts = analyze("demo/x.pdf", [N - 1])     # 0-based page indices
   for r in pages[0].rows: print(round(r.baseline, 1), r.box, r.text[:80])
   document = build_document(doc, pages, stats, layouts)
   ```
   Monkeypatching a function such as `structure.ended_short` with a printing wrapper is the quickest way
   to see why two lines were or were not joined.
2. **Fix the cause, generally.** Thresholds are in multiples of the body font size (`self.body`,
   `stats.body_size`) or the line pitch (`stats.line_step`), never absolute points. Check the gotchas in
   `reference/architecture.md`: pass order in `PageAnalyzer.run` matters, and so does first-come segment
   ownership.
3. **Test fast:** `.venv/bin/python -m pytest -q -m "not corpus"`. Then lint:
   `.venv/bin/ruff check src tests tools --select F,E9,B --ignore B007,B905,B008`. Where you can, add a
   synthetic regression test in `tests/` (see `PdfBuilder` in `tests/conftest.py`).
4. **Run the gate:** `.venv/bin/python tools/corpus_gate.py --keep /tmp/new` (about 90 s for 12 papers
   with `--jobs 4`). Each entry reports `improved`, `same` or `REGRESSED` with the reasons. A regression
   is: any metric down more than 0.002, the total lint count up, or any blank-image,
   duplicate-paragraph or hyphen-leftover count up.
5. **Review what changed, even when the gate passes.** The metrics cannot see every visual regression:
   ```bash
   .venv/bin/python tools/epub_diff.py demo/<name>.epub /tmp/new/<name>.epub --out /tmp/diff/<name> --context 1
   ```
   It prints a diff of the reading flow (one line per block with page and alt texts) and saves old and
   new versions of every changed image. View the images and check doubtful pages against
   `pdf2epub inspect`. For a large change, have independent reviewers do this per paper, and tell them to
   look for regressions specifically.
6. **Accept:** `.venv/bin/python tools/corpus_gate.py --update`. It refuses if anything regressed. Then
   commit the code, `demo/*.epub`, `demo/*.quality.json` and `demo/README.md` together. Push.
7. **The pytest version of the gate** is `pytest -m corpus`. It is slower and serial; the tool is better
   while iterating.

## Delivering many papers, or a long session

- `tools/run_corpus.py` downloads and converts a list of arXiv ids into `.corpus/` (gitignored). Use it
  for exploratory runs on papers that are not (yet) in the corpus.
- `demo/` is ~125 MB and grows with each paper. If it gets unwieldy, propose moving `demo/*.pdf` and
  `demo/*.epub` to Git LFS to the user; don't do it unasked.
